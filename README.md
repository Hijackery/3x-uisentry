**Русский** · [English](README.en.md)

Telegram-бот для сервера с панелью 3X-UI: следит за железом, systemd-сервисами
и панелью, присылает алерты, показывает подписки и трафик. Опасные действия
(рестарт сервиса, xray, обновление системы, перезагрузка) выполняются только
с подтверждением кнопкой и только администратором.

## Возможности

- **Мониторинг** — система, systemd-службы, панель 3X-UI, xray, inbound'ы,
  подписки и трафик; почасовые средние за сутки.
- **Алерты** — гистерезис (без «дребезга»), кулдаун и мьют «знаю, до утра»;
  под алертом сразу кнопки «Рестарт» и «Журнал».
- **Безопасные действия** — рестарт сервиса и xray, `apt` (full и phased),
  проверка релиза, перезагрузка: только с подтверждением, с журналом действий.
- **Установка одной командой** — мастер спрашивает токены сразу, проверяет
  токен `@BotFather` и доступность панели, в конце — самопроверка из 8 пунктов.
- **Любой популярный Linux** — systemd, OpenRC (Alpine, Gentoo), SysVinit;
  пакетные менеджеры `apt`/`dnf`/`yum`/`zypper`/`pacman`; Python 3.10+.
- **Панель `xui-menu`** — правки настроек, рестарт, журнал и обновление из
  терминала, секреты всегда маскируются.

## Как устроено

```text
Telegram  ⇄  бот (непривилегированный пользователь xui-monitor)
                 ├─ psutil / systemctl / journalctl   — метрики и службы
                 ├─ API панели (Bearer, scope node-sync) — inbound'ы, подписки, рестарт xray
                 └─ sudo xui-ctl (узкий sudoers)      — рестарт, apt, reboot, журнал
```

Секреты лежат в `.env` (`640 root:xui-monitor`), состояние — в SQLite
(`/var/lib/xui-monitor`), код принадлежит `root`. Подробности — в разделе
[Безопасность](#безопасность) и [SECURITY.md](SECURITY.md).

## Что нужно

- Linux; менеджер служб определяется автоматически: **systemd**
  (Debian/Ubuntu, RHEL/CentOS/Rocky/Alma, Fedora, openSUSE, Arch/Manjaro) или
  **без systemd** — OpenRC (Alpine, Gentoo) и SysVinit. Пакетный менеджер тоже
  определяется сам (`apt`/`dnf`/`yum`/`zypper`/`pacman`). Выбрать вручную:
  `--init systemd|openrc|sysv`.
- Python 3.10+ — установщик подберёт подходящий интерпретатор сам.
- Панель 3X-UI и её API-токен.
- Бот в Telegram (токен от [@BotFather](https://t.me/BotFather)) и ваш numeric ID
  (узнать: [@userinfobot](https://t.me/userinfobot)).

## Установка

```bash
bash <(curl -Ls https://raw.githubusercontent.com/Hijackery/xui-monitor-bot/main/install.sh)
```

или через пайп:

```bash
curl -fsSL https://raw.githubusercontent.com/Hijackery/xui-monitor-bot/main/install.sh | sudo bash
```

Скрипт сам скачает код, спросит токены, поставит зависимости, создаст системного
пользователя `xui-monitor`, включит автозапуск и в конце проверит, что всё
работает. **Мастер задаёт вопросы сразу — четвёртым шагом, до установки
зависимостей,** поэтому отвечать нужно в начале. Если `.env` остался от
прерванного запуска, мастер дозаполнит недостающие значения (существующие
подставит как значения по умолчанию) — править файл руками не нужно. Вопросы читаются с терминала,
поэтому диалог идёт и при установке через пайп.

GitHub может отдавать ветку из кэша пару минут после обновления репозитория —
если увидели старую версию, просто повторите команду чуть позже. Архив с кодом
скачивается с меткой времени и всегда актуален.

Лишние пробелы и завершающие слэши в адресе (`https://host:5580/`) установщик
убирает сам, а поле `webBasePath` — это **отдельная настройка «URL панели»** в
3X-UI (обычно `/`, то есть поле оставляют пустым). Путь `/panel` из адресной
строки вводить не нужно: в 3X-UI интерфейс всегда живёт на `.../panel`, и если
вписать это в `webBasePath`, получится лишний сегмент `.../panel/panel/api`.
Установщик сам проверяет адрес перед запросом токена и молча исправляет путь,
если тот не подтвердился; если в поле случайно вставить полный адрес — тоже
поймёт и поправит.

Токен создаётся **в самой панели 3X-UI** (не в Telegram и не в боте):

1. **3X-UI v3.x:** «Настройки панели → Учётная запись → API-токен» → создать
   токен со scope **`node-sync`** (или `admin`). **3X-UI 2.x:** «Настройки →
   API Tokens».
2. Scope `node-sync` открывает список inbound'ов и подписки — это то, что нужно
   боту. `monitor` даёт только статус и не подойдёт.
3. **Скопируйте значение сразу**: панель (v3) показывает токен только при
   создании, позже — лишь «задано». Это значение и есть `PANEL_API_TOKEN`.

В v3 команда `sudo x-ui setting -getApiToken` новых админ-токенов не создаёт, а
ротирует служебный `cli-fallback`: создавайте токен в интерфейсе или через API —
`POST /panel/api/setting/apiTokens/create` с `name`, `scope` (`node-sync` или
`admin`) и `expiresAt` (значение в ответе отдаётся один раз).

Проще всего выпустить токен из терминала сервера (команда напечатает значение):

```bash
sudo x-ui setting -getApiToken true -tokenName monitor-bot -tokenScope node-sync
```

Проверить, что токен рабочий (ответ должен быть `{"success":true,…}`):

```bash
curl -fsS -H "Authorization: Bearer <токен>" \
  https://panel.example.com:2053/panel/api/server/status
```

Установщик делает эту же проверку сам, а если поле оставить пустым и панель
запущена — выпустит токен автоматически.

Без вопросов (значения из окружения):

```bash
sudo env \
  TELEGRAM_BOT_TOKEN='123456789:AA...' \
  TELEGRAM_ADMIN_IDS='11111111' \
  PANEL_URL='https://panel.example.com:2053' \
  PANEL_API_TOKEN='...' \
  bash install.sh --yes
```

Полезные опции: `--repo owner/name`, `--ref ветка`, `--prefix DIR`,
`--user NAME`, `--no-start`, `--force-config`, `--print-source` (показать, откуда
будет взята версия), `--sha256 HASH`,
`--init TYPE`, `--menu`. Полный список — `--help`.


## Меню настроек (`xui-menu`)

После установки в системе появляется консольная панель — быстрее, чем править
`.env` руками:

```bash
sudo xui-menu          # интерактивное меню
sudo xui-menu show     # текущие настройки (секреты замаскированы)
sudo xui-menu keys     # какие ключи разрешено менять
xui-menu check PANEL_TIMEOUT 20   # проверка значения без изменений (без root)
sudo xui-menu set PANEL_TIMEOUT 20
sudo xui-menu restart       # применить
sudo xui-menu restart-xray  # перезапустить xray в панели (через API)
sudo xui-menu logs 100
```

Интерактивное меню рисуется в рамке и сгруппировано по разделам; сверху видно
состояние службы:

```text
╔════════════════════════════════════════════════════════╗
│       Бот мониторинга 3X-UI — панель управления        │
│  Служба xui-monitor-bot: ● работает                    │
│   Диагностика                                          │
│    1. Состояние службы и последние ошибки              │
│    2. Показать настройки (секреты замаскированы)       │
│    3. Журнал бота (последние 50 строк)                 │
│────────────────────────────────────────────────────────│
│   Telegram                                             │
│    4. Токен бота (@BotFather)                          │
│    5. ID администраторов                               │
│    6. Чат для алертов                                  │
│   …                                                    │
│   22. Удалить бота                                     │
│    0. Выход                                            │
╚════════════════════════════════════════════════════════╝
```

Что делает каждый пункт:

| Пункт | Действие |
|---|---|
| 1 | `systemctl status` + последние предупреждения из журнала бота |
| 2 | показать настройки; токены замаскированы (`123456 ···a1b2`, короткие — `*** (N символов)`) |
| 3 | журнал бота (50 строк) |
| 4–6 | пошаговая смена токена бота, ID админов, чата для алертов |
| 7–9 | адрес панели, `webBasePath`, API-токен панели |
| 10 | проверка TLS (`PANEL_VERIFY_TLS`) и CA-сертификат (`PANEL_CA_BUNDLE`) |
| 11–13 | пороги CPU / памяти / диска (подменю: предупреждение и критично) |
| 14 | гистерезис и кулдаун алертов |
| 15 | за сколько дней предупреждать об окончании подписки |
| 16–17 | службы под наблюдением, уровень логирования |
| 18 | правка любого ключа из белого списка по имени (`xui-menu keys`) |
| 19 | перезапуск бота с проверкой, что служба активна |
| 20 | перезапуск xray в панели через API (с подтверждением) |
| 21 | обновление: скачивает свежий установщик из ветки `main` и запускает его с тем же `PREFIX`; если сети нет — берёт локальную копию `/opt/xui-monitor-bot/install.sh` |
| 22 | удаление; меню отдельно попросит ввести `yes` |

Что важно знать:

- ввод проверяется: неверный номер даёт подсказку с диапазоном (`0–22`), `q`
  или пустая строка перерисовывают меню; рамка подстраивается под длину строк;
- менять можно только ключи из белого списка (`xui-menu keys`); значения
  проверяются до записи (`check`) — например, `LOG_LEVEL` принимает лишь
  `DEBUG/INFO/WARNING/ERROR`, а `PANEL_URL` обязан начинаться с `http`;
- `.env` перезаписывается атомарно с правами `640 root:<сервисный пользователь>`,
  как при установке; правки применяются после перезапуска (меню предложит);
- секреты никогда не печатаются целиком, и `.env` не нужно никому пересылать —
  в нём лежат оба токена;
- пути можно переопределить: `sudo PREFIX=/opt/бот ENV_FILE=/opt/бот/.env xui-menu`;
- автоочистку экрана можно выключить: `XUI_MENU_NO_CLEAR=1 sudo xui-menu`.

### Если в системе нет systemd

Установщик поставит `/etc/init.d/xui-monitor-bot` (`start`/`stop`/`status`/
`restart`) и зарегистрирует автозапуск через `rc-update` (OpenRC) либо
`update-rc.d`/`chkconfig` (SysVinit). Управление, `.env`, sudoers-обёртка и
`xui-menu` работают так же; журнал берётся из файла `bot.log`, если `journalctl`
недоступен. Отличия: нет systemd-изоляции юнита, а `/services` показывает, что
состояние служб недоступно (бот напишет об этом в «Требует внимания»).

## Обновление и удаление

```bash
# обновить (конфиг и состояние сохранятся)
bash <(curl -Ls .../install.sh)

# удалить бота целиком: служба, sudoers, обёртка, меню, код, база и пользователь
sudo bash install.sh --uninstall

# оставить базу и пользователя (например, чтобы сохранить журнал действий)
sudo bash install.sh --uninstall --keep-state

# интерактивное меню
sudo bash install.sh --menu
```

## Команды

| Команда | Что показывает |
|---|---|
| `/status` | общая сводка: сервер, сервисы, панель, трафик |
| `/services` | состояние systemd-юнитов, рестарт, журнал |
| `/panel` | доступность панели и xray, версии, обновления |
| `/subs` | подписки: сроки, трафик, отключённые |
| `/history` | почасовые средние CPU/RAM/диска за сутки |
| `/logs` | журнал выбранного сервиса |
| `/audit` | журнал действий бота |
| `/maint` | обслуживание: apt (full-upgrade и phased upgrade), релиз-обновление, произвольная команда |
| `/help` | помощь простыми словами: что нажать и что значат цифры (кнопка «❓ Помощь») |

Кнопки под сообщениями дублируют команды: у каждого экрана есть «🏠 В меню», так
что в тупике оказаться нельзя. Гостям бота кнопки не показываются.

Команды и кнопки работают **только в личном чате** администратора: в группе бот
отвечает отказом, чтобы адреса, подписки и трафик не утекли в общий чат.

`/status` начинается с вердикта одной строкой (`всё в норме` / `сервисы не
работают: …`), замечания идут сразу за ним, а детали спрятаны за
`📋 Подробнее` — ночью достаточно одного экрана. Метрики выровнены
моноширинным блоком, время подписано «время сервера».

Кнопки собирают данные с промежуточным «⏳», после действия остаются
контекстные кнопки (например, журнал перезапущенного сервиса). Под алертом
сразу есть `♻️ Рестарт <сервис>`, `📜 Журнал` и `😴 Знаю, до утра` — заглушить
конкретную проблему на 8 часов (мьют хранится в SQLite и переживает
перезапуск). Журнал сервиса умеет `🔎 Только ошибки` и `📜 Ещё 200 строк`,
а `/audit` — фильтры «отказы / действия». Подтверждения объясняют последствия
(«панель и VPN отключатся на 1–2 минуты»). Перезагрузка сервера — в `/maint`
→ `🔻 Перезагрузить сервер`, за подтверждением.

## Настройки

Все параметры — в `/opt/xui-monitor-bot/.env`, пример с комментариями —
[`.env.example`](.env.example).

| Ключ | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather |
| `TELEGRAM_ADMIN_IDS` | ID администраторов через запятую |
| `ALERT_CHAT_ID` | чат для алертов (пусто — админам в личку) |
| `TELEGRAM_API_URL` | свой Bot API или прокси (по умолчанию официальный) |
| `PANEL_URL` | адрес панели: IP или домен, например `https://panel.example.com:2053` (если в панели задан «Домен панели», указывайте именно его) |
| `PANEL_BASE_PATH` | `webBasePath` панели, если задан |
| `PANEL_API_TOKEN` | токен панели (scope `node-sync`) |
| `PANEL_VERIFY_TLS` | проверять TLS-сертификат панели (по умолчанию `true`) |
| `PANEL_CA_BUNDLE` | свой CA-файл (PEM) для панели; перекрывает `PANEL_VERIFY_TLS` |
| `PANEL_TIMEOUT` | таймаут запросов к панели, сек |
| `SERVICES` | юниты под наблюдением, через запятую (`x-ui,fail2ban`) |
| `DISK_PATH` | что проверять по месту |
| `CPU_WARN` | порог предупреждения по CPU, % |
| `CPU_CRIT` | порог критического CPU, % |
| `MEM_WARN` | порог предупреждения по RAM, % |
| `MEM_CRIT` | порог критического RAM, % |
| `DISK_WARN` | порог предупреждения по диску, % |
| `DISK_CRIT` | порог критического диска, % |
| `ALERT_HYSTERESIS` | на сколько % метрика должна отойти назад, чтобы сбросить алерт |
| `ALERT_COOLDOWN` | как часто повторять активный алерт, сек |
| `EXPIRING_SOON_DAYS` | за сколько дней подписка считается истекающей |
| `CHECK_INTERVAL` | период фоновой проверки, сек (минимум 15) |
| `ACTION_COOLDOWN` | пауза между одинаковыми действиями, сек |
| `CONFIRM_TTL` | сколько живёт кнопка подтверждения, сек |
| `COMMAND_TIMEOUT` | таймаут разрешённых команд, сек |
| `COMMAND_ALLOWLIST` | список команд для диагностики (должен совпадать с `install/xui-ctl`) |
| `STATE_PATH` | база SQLite |
| `LOG_PATH` | файл лога |
| `LOG_LEVEL` | `DEBUG` / `INFO` / `WARNING` / `ERROR` |
| `SUDO_WRAPPER` | путь к `xui-ctl` |

`PANEL_URL` принимает и IP, и домен. Два практических правила:

- если в панели задан **«Домен панели»** (`webDomain`), 3X-UI сверяет заголовок
  `Host` и отвечает `403` на всё остальное — тогда в `PANEL_URL` должно быть
  ровно это имя, а не IP;
- имя должно резолвиться **с самого сервера** (бот работает там же). Если домен
  указывает на публичный IP и обратного NAT нет, используйте
  `http://127.0.0.1:2053` с тем же `PANEL_BASE_PATH`. IPv6 пишите в скобках:
  `http://[::1]:2053`.

Проверить быстро: `curl -fsS -o /dev/null -w '%{http_code}\n' https://ваш-домен:5580/panel/`
(`403` — как раз сработала проверка домена).

`http` или `https` — работают оба, но выбирать стоит по ситуации:

- панель и бот на одном сервере, панель слушает localhost → берите
  `http://127.0.0.1:2053` (+ `PANEL_BASE_PATH`): трафик не выходит за пределы
  машины, TLS не нужен;
- панель доступна по публичному адресу → только `https://`, иначе токен и
  содержимое API (inbound'ы, клиенты, подписки) идут открытым текстом. Для
  самоподписанного сертификата не отключайте проверку, а укажите `PANEL_CA_BUNDLE`;
- указали `http`, а панель отвечает редиректом на `https`? Установщик скажет об
  этом прямо («панель ответила редиректом»), а бот не пойдёт по редиректу —
  просто поменяйте схему на `https://`.

### Куда приходят алерты

`ALERT_CHAT_ID` можно оставить пустым — тогда алерты приходят в личку всем ID из
`TELEGRAM_ADMIN_IDS`. Если нужен общий чат: добавьте туда бота, отправьте любое
сообщение и узнайте ID чата (`@userinfobot`, `@getidsbot`); у групп и каналов он
отрицательный, например `-1001234567890`. Учтите, что в алертах есть адреса,
подписки и трафик — в общей группе их увидят все участники; команды при этом
всё равно принимаются только в личном чате администратора.

Переменные окружения процесса имеют приоритет над файлом `.env`.

## Безопасность

- Бот работает непривилегированным пользователем `xui-monitor`; код и venv
  принадлежат root, `.env` доступен сервису только на чтение.
- Все привилегированные операции идут через `/usr/local/bin/xui-ctl` и узкий
  sudoers-список из **точных команд** (без шаблонов в аргументах — так требуют и
  классический sudo, и `sudo-rs` в Ubuntu 26.04+); произвольного shell нет. `apt` выполняется отдельным
  transient-юнитом systemd, потому что сервис живёт с `ProtectSystem=strict`.
- Опасные действия требуют подтверждения, токен привязан к запросившему
  администратору, всё пишется в `audit_log`.
- Клиент панели не следует редиректам (иначе токен мог уйти на чужой хост),
  значения из панели экранируются перед отправкой, токен бота не попадает в
  логи даже на `DEBUG`.
- Повторы защищены: одно подтверждение срабатывает один раз, одинаковые действия
  ограничены `ACTION_COOLDOWN` (включая рестарт xray), а сообщения, которые
  Telegram отклонил из-за flood control, отправляются повторно.
- Команды принимаются только в личном чате; попытки доступа посторонних
  пишутся в журнал (`denied`), чтение журнала сервисов ограничено по частоте.
- Нестандартный `TELEGRAM_API_URL` отмечается предупреждением в логе, а
  установщик умеет проверять контрольную сумму архива (`--sha256`).
- Секреты не попадают в логи: сторонние логгеры (`telegram`, `httpx`) приглушены,
  а поверх стоит форматтер, который вырезает токен бота из URL и точные значения
  токенов из конфигурации — в том числе из текста исключений. Telegram ID в
  сообщениях маскируются (`…789`), `xui-menu show/check` не печатают секреты.
- Для самоподписанного сертификата панели есть `PANEL_CA_BUNDLE`: вместо
  отключения проверки TLS можно подсунуть свой CA и держать пиннинг.

### Защита от спама и «случайной поломки»

- Любое изменение сервера требует подтверждения кнопкой; токен подтверждения
  одноразовый и привязан к тому администратору, кто его запросил.
- Паузы: `ACTION_COOLDOWN` (по умолчанию 30 с) — для действий, 5 с — на чтение
  журнала, 2 с — на «Обновить». Кнопкой нельзя устроить нагрузку на панель.
- `apt` выполняется отдельным transient-юнитом, и второй запуск невозможен, пока
  идёт первый; сама команда фиксирована.
- Бот **не умеет** запускать произвольные команды (`run_command` — шесть
  литералов из белого списка), удалять файлы, править конфиги системы, писать в
  `/usr`, `/boot`, `/etc`. Привилегии ограничены узким sudoers-правилом на
  `/usr/local/bin/xui-ctl`.
- Ресурсы службы ограничены (`MemoryMax=256M`, `TasksMax=64`), вывод команд
  обрезается (16 КБ) и имеет таймаут, база чистится по расписанию.
- Telegram-нагрузка ограничена: при flood control не больше 3 попыток и не
  дольше 30 с, длинные сообщения режутся по строкам.

## Если что-то не работает

```bash
systemctl status xui-monitor-bot
journalctl -u xui-monitor-bot -n 50 --no-pager
```

- «Синтаксис sudoers невалиден» — установщик печатает строку от `visudo`; пришлите
  её в issue: правила генерируются, и это наша ошибка, а не ваша.
- «Системные метрики недоступны: `/proc/stat`» — обновите юнит службы
  (в старых установках была директива `ProcSubset=pid`, она прячет `/proc/stat`):
  `sudo sed -i '/^ProcSubset=/d' /etc/systemd/system/xui-monitor-bot.service &&
  sudo systemctl daemon-reload && sudo systemctl restart xui-monitor-bot`.
- Ubuntu 26.04 и новее: там `visudo` переписан на Rust (`sudo-rs`), он запрещает
  шаблоны в аргументах и не знает части `Defaults` — установщик это учитывает и
  перечисляет команды точно, ручная правка не нужна.
- «Токен отклонён» — проверьте `TELEGRAM_BOT_TOKEN` и `PANEL_API_TOKEN`
  (удобнее через `sudo xui-menu` → «Показать настройки» / «Сменить токен бота»).
- `inbounds/list недоступен` — у токена панели нет scope `node-sync`.
- Логи сервиса не видны — проверьте, что в sudoers есть правило `journal`.
